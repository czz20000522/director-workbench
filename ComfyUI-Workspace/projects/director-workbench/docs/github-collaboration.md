# GitHub 协作约定

公开仓库：https://github.com/czz20000522/director-workbench

## 用户与客户端 Agent

遇到 bug 或能力缺口，先搜索 GitHub Issues，重复问题补充已有 Issue。提供操作步骤、预期和实际行为、客户端系统、版本及脱敏截图/日志。不同设备使用同一个问题追踪入口。

不要公开密码、API key、Bearer/Cookie、OAuth 回执、账号信息、Tailscale 地址/主机名、SSH 配置、个人路径、作品素材或完整服务日志。安全漏洞及泄露凭据不要发布到公开 Issue，先通过已有私人渠道通知维护者；泄露凭据立即撤销。

## 本机维护 Agent

接手时阅读 AGENTS.md、本约定及相关 Issue/PR。GitHub Issues 是问题状态和验收的唯一持续维护来源；本地 ISSUES.md 及迁移备份已退役删除。迁移项保留 DW 编号，新问题使用 GitHub 编号。

1. 复现问题并记录原因、影响和验收条件；无法复现时记录缺失证据。
2. 为每项修复创建 `codex/issue-<编号>-<说明>` 分支。只修改必要文件，不夹带作品、运行数据或无关本地修改。
3. 运行相关验证，创建 PR，关联 Issue；描述原因、修复、实际测试和剩余限制。修复完成且符合验收才使用 `Fixes #编号`；部分进展使用 `Refs #编号`。
4. 合并由已获授权的维护者执行。代码合并不代表生产已部署；需要跨设备或 GPU 验收的问题，在最终验收前保持开放，PR 使用 `Refs`。
5. 在 Issue 留下原因、修复方式、验证结果、剩余限制四项回复。部署/重启服务/长时间 GPU 生成仍遵守原有授权边界。

公开操作必须有本次用户授权；读取公开问题无需额外确认。定时轮询/自动合并/部署不因本约定自动启用。

## 发布边界

仓库保留 Comfy-Desktop 相对目录布局，只发布筛选过的工作台源代码及运行必需的共享脚本。不上传旧 Git 历史、配置、环境、模型、作品、数据库、生成结果、诊断和历史私人文档。首次发布已使用独立快照建立新历史，本机根目录现已接到同一公开仓库。后续直接在本机源代码分支工作，提交前检查暂存区和隐私；根 .gitignore 为逐文件白名单，新源文件需审查后添加。`tools/export_public_source.py` 可用于独立导出审查，不能据此绕过白名单。不得恢复或推送旧本机历史。

依赖版本、代码发布和本机服务状态分别记录。公开可见不自动授予开源许可证；添加许可证需由权利人决定。
